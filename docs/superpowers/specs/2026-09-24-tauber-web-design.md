# Сайт Таубер: перенос прототипа в код

Дата: 2026-09-24
Статус: на согласовании

## Зачем это делается

Готовый прототип сайта Таубер живёт в Claude Design одним файлом на 352 КБ. Дизайн закончен, дальше нужно наполнять сайт содержанием: характеристиками продукции, текстами, фотографиями. Делать это в прототипе нельзя по двум причинам.

Первая: один файл на 3767 строк уже упирается в технические потолки, и любая правка вдвоём в нём означает конфликт — двое не могут одновременно менять один файл.

Вторая: прототип не является сайтом. Его нельзя опубликовать в интернете, отдать поисковикам и показать клиенту по ссылке.

Поэтому прототип переносится в код: дизайн сохраняется один в один, а содержание выносится в отдельные файлы, которые можно править, не касаясь вёрстки.

## Кто работает и как

Над сайтом работают двое: Денис и коллега. Оба вносят изменения, изменения должны доезжать друг до друга.

Схема — приватный репозиторий на GitHub с доступом на двоих. Правки приходят в `main` через pull request. При слиянии в `main` сайт автоматически пересобирается и публикуется.

Серверную защиту `main` включить нельзя: на бесплатном тарифе GitHub она недоступна для приватных репозиториев, а делать репозиторий публичным ради неё не стоит — тексты и прайсовая информация стали бы видны всем. Проверено на существующем репозитории аккаунта. Поэтому защита держится на двух вещах: договорённости работать через pull request и локальной проверке, которая ставится на обе машины и отказывается отправлять правку напрямую в `main`. От случайной ошибки это защищает, от намеренного обхода — нет, и для двоих участников этого достаточно. Если в проекте появятся третьи лица, вопрос возвращается: тогда имеет смысл GitHub Pro с настоящим серверным запретом.

Отдельно оговорено: git не даёт одновременного редактирования одного файла в реальном времени, как Google Docs или Claude Design. Он даёт другое — каждый работает у себя, обменивается правками за секунды, ничего не теряется, любое изменение можно откатить. Чтобы одновременная работа была бесконфликтной на практике, содержание разносится по отдельным файлам: по файлу на категорию и на товар. Тогда двое физически работают в разных файлах.

## Как ведём работу: по разделу за заход

Дизайн — сырая версия. Каждый раздел будет обсуждаться, наполняться и, возможно, переделываться по ходу. Поэтому переносить все 28 страниц одним заходом нельзя: значительная часть работы уйдёт в мусор при первой же переделке.

Работа идёт циклом, по одному разделу: обсудили → перенёс и наполнил → посмотрели по ссылке → поправили → следующий. Каждый раздел уходит отдельным pull request и получает свою ссылку для просмотра, так что результат виден до слияния.

Исключение — каркас: шапка, футер, мобильное меню, цвета, шрифты и главная страница. Он от сырости разделов не зависит, поэтому делается первым и целиком, вместе с публикацией.

Переделка раздела стоит дёшево именно потому, что содержание разложено по отдельным файлам: правка одного раздела не задевает остальные.

## Где живёт дизайн

После переноса каркаса дизайн ведётся в коде. Прототип в Claude Design остаётся архивом-эталоном и больше не правится.

Изменения оформления описываются словами — «плитки в каталоге крупнее», «убрать плашку», «поменять порядок блоков», — вносятся в код, и результат смотрится на живом сайте по постоянной ссылке.

Причина такого решения: дизайн будет много меняться, а две параллельные версии — прототип и сайт — неизбежно расходятся, и со временем перестаёт быть понятно, где правда. Плюс каждая правка делалась бы дважды.

## Что уже перенесено

В папке `design/` лежат исходные материалы, забранные из Claude Design и из экспорта `Сайт Tauber.html`:

- `Tauber.dc.html` — полный эталон прототипа, 352 КБ, 3767 строк
- `assets-web/` — 156 изображений продукции в формате WebP
- `fonts/` — Golos Text и Material Symbols, локальные файлы шрифтов
- `unnamed/` — 32 изображения, подключённые в прототипе без имён файлов; подписи для опознания собраны в `ASSETS-MAP.md`
- `TAUBER_макеты_сайта_22-09-2026.pdf` — макеты страниц

Папка `design/` остаётся в репозитории насовсем: это эталон для сверки и он должен быть виден обоим участникам.

## Что за сайт получается

**Главная** — каталог направлений. Раскладка каталога «5 × 2», блок отраслей в варианте «Крупный шрифт». Остальные варианты, которые перебирались в прототипе, в код не переносятся.

**Десять страниц категорий** на общем шаблоне: Трубопроводы, Гидрантная система, Фильтры топливные и жидкостные, Обслуживание самолёта на стоянке, ПИТ-системы, Кэдди, Фильтрационные модули, Слив и налив, Автоматизированные наливные комплексы, Пробоотборники.

**Семнадцать продуктовых страниц**, у каждой своя вёрстка: `ftv`, `psi`, `pape`, `cable`, `plug`, `power`, `pca`, `panto`, `dab`, `fmk`, `s1201`, `s1803`, `ank`, `prb`, `probe`, `pitp`, `cdm`.

**Общее для всех страниц:** шапка с меню, мобильное меню, футер, форма заявки, галерея фотографий производства, табы на продуктовых страницах, фильтр подбора.

## Стек

Astro. Сайт собирается в статические страницы: грузится мгновенно, хорошо индексируется поисковиками, хостинг почти бесплатный. Содержание лежит отдельными файлами данных, вёрстка — отдельно. Блоки прототипа переносятся в компоненты почти один в один, потому что в прототипе они уже разделены.

Next.js рассмотрен и отклонён: он нужен под личный кабинет, серверные расчёты и интеграции, чего в планах нет. Набор статических HTML-файлов без сборки отклонён тоже: шапка и футер продублировались бы в 28 страницах, и смена телефона превратилась бы в 28 правок.

## Структура проекта

```
src/
  layouts/      каркас страницы: шапка, футер, мобильное меню, мета-теги
  components/   блоки: карточка товара, таблица характеристик, табы,
                галерея производства, фильтр подбора, форма заявки
  pages/        главная, каталог, категории, продуктовые страницы
  styles/       дизайн-токены: цвета, шрифты, отступы
content/        ← здесь работают Денис и коллега
  catalog/      по файлу на категорию
  products/     по файлу на товар
  pages/        тексты отдельных страниц
  site.json     телефон, адрес, почта — в одном месте на весь сайт
public/
  images/       изображения продукции
  fonts/        локальные шрифты
design/         эталон прототипа, макеты, карта изображений
docs/           эта спецификация и инструкция для коллеги
```

Принцип разделения: всё, что меняется при наполнении, лежит в `content/`. Всё, что определяет внешний вид, — в `src/`. Правка характеристик товара не может сломать вёрстку, потому что находится в другом файле.

## Как переносится содержание

В прототипе содержание уже отделено от вёрстки: страницы категорий берут данные из объекта `DATA`, где ключ — это страница, а продуктовые страницы — из отдельных наборов значений.

Категории переносятся один к одному: каждый ключ `DATA` становится файлом в `content/catalog/`. Набор полей сохраняется: хлебная крошка, заголовок, вводный текст, кнопка, главное изображение, плашка, число с подписью, перечисление преимуществ, заголовок раздела, карточки.

Продуктовые страницы переносятся по одной, каждая в свой файл в `content/products/`, со своим набором полей — у них вёрстка индивидуальная.

Навигация в прототипе работает через внутреннее состояние: одна страница подменяет другую. В коде это становится обычными адресами страниц, чтобы на каждую можно было дать ссылку и чтобы её видели поисковики.

## Дизайн-токены

Взяты из прототипа: фон `#E9EFEB`, светлая подложка `#EDF2EE`, оранжевый акцент панелей `#F5761B`, тёмная панель `#1C1F21`, основной текст `#101214`, красный `#E31E24` на ссылках при наведении. Шрифт Golos Text, иконки Material Symbols.

В бандл прототипа попал только вес 400. Веса 500–800, которые использует дизайн, дотягиваются локально при переносе, чтобы сайт не зависел от Google Fonts.

Ширина макета в прототипе фиксированная, 1600 пикселей. В коде это становится адаптивной сеткой: на телефоне и планшете страницы должны читаться, иначе половина посетителей увидит сайт сломанным. Мобильное меню в прототипе уже предусмотрено.

## Форма заявки

В прототипе форма нарисована и собирает поля, но никуда их не отправляет. Чтобы заявки приходили, нужно выбрать адресата: почта, Telegram или CRM. Решение не влияет на выбор стека и принимается на этапе наполнения. До этого форма проверяет заполнение и показывает сообщение об успехе, но письма не уходят.

## Что не входит в эту работу

Многоязычность, личный кабинет, интеграция с 1С, онлайн-оплата, расчёт цен на сервере, блог. Ничего из этого в прототипе нет и в планах не заявлено.

## Порядок работ

Двадцать восемь страниц — это слишком много для одного захода, поэтому работа разбита на этапы. Каждый этап заканчивается чем-то, что можно открыть и посмотреть.

**Этап 1. Репозиторий и доступ.** Создаётся приватный репозиторий на GitHub, коллега добавляется соавтором, на обе машины ставится локальная проверка против прямого пуша в `main`. Сюда же попадают материалы из `design/`. Смысл делать это первым: коллега подключается сразу и видит всё, что происходит дальше.

**Этап 2. Каркас и главная.** Astro-проект, дизайн-токены, шрифты, изображения, шапка, футер, мобильное меню — и главная страница с каталогом. Результат: работающая главная, открывается в браузере, выглядит как прототип.

**Этап 3. Публикация.** Автоматическая сборка и публикация при слиянии в `main`. После этого любая правка становится видна на живом сайте без чьего-либо участия — в том числе правка, которую сделал коллега.

**Этап 4 и далее. Разделы, по одному за заход.** Порядок задаёт Денис, исходя из того, что важнее для продаж. Для каждого раздела: обсуждаем содержание и вид, я переношу и наполняю, смотрим по ссылке, правим, сливаем. Десять категорий и семнадцать продуктовых страниц проходят через этот цикл; сколько их за раз — решается по ходу, а не планируется заранее.

**Последний этап. Форма заявки.** Подключается отправка выбранным способом, проверяется, что заявка доходит. Делается в конце, когда понятно, с каких страниц приходят обращения.

Этапы 1–3 имеет смысл сделать подряд и без пауз: до них совместная работа невозможна и обсуждать разделы не на чем, а после них цикл работает полностью — правка видна на сайте через минуту после слияния.

## Открытые вопросы

1. Куда отправлять заявки с формы — решается при наполнении.
2. Написание бренда в адресах и заголовках: папка называется Tauber, проект в Design — «Сайт Таубер». Нужно одно написание, чтобы не зашивать опечатку в код.
3. Тридцать два изображения из `unnamed/` не имеют имён. Опознаются визуально при сборке соответствующих страниц; возможно, часть из них — старые версии и не нужна.
4. Домен и хостинг: есть ли действующий домен, куда публиковать сайт.
